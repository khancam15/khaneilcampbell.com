Case study 02 · Security · Mar to Apr 2026

Turning authentication noise into analyst-ready signal.

Problem

Failed logons are constant. Most are typos; a few are attacks.

Role

Sole builder: lab, attack, detection and triage write-up.

Tools

Splunk Enterprise, SPL, Python, Kali Linux, VirtualBox.

Result

80+ failed logons isolated in a defined window.

The problem

Failed logons are constant in any Windows estate. Most are a mistyped credential; a few are not. The goal was to find the difference reliably: identify anomalous authentication patterns, cut alert fatigue through threshold tuning, and turn raw event data into a structured, repeatable response.

It is deliberately unglamorous work. The value is in the write-up: anyone picking this up later should be able to rebuild the query, understand why the threshold sits where it does, and follow the same triage path.

My role

I built the lab in VirtualBox, ran an SMB brute-force attack from Kali Linux against a Windows 11 host, wrote the SPL detection and threshold alert in Splunk, and generated triage case notes in Python through the Splunk REST API.

The workflow

  1. IngestEvent ID 4625

    Windows Security logs ingested into Splunk Enterprise and normalized by host, account and time.

  2. DetectSPL correlation

    Failed logon volume correlated across source IP, account and time window.

  3. TriageTuned threshold

    Thresholds adjusted to cut false positives without losing signal, with decisions written down.

  4. RespondCase notes

    Analyst actions, escalation criteria and reusable case notes for the next occurrence.
