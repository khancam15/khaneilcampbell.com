Case study · Published

Authentication log analysis with Splunk.

Brute-force credential detection: SPL alert logic, a structured triage method, and a response workflow designed to be run again by someone who was not there.

View the repository Back to labs
Objective

Turn authentication noise into analyst-ready signal.

Failed logons are constant in any Windows estate. Most are a mistyped credential; a few are not. The goal was to find the difference reliably — identify anomalous authentication patterns, cut alert fatigue through threshold tuning, and turn raw event data into a structured, repeatable response workflow.

It is deliberately unglamorous work. The value is in the write-up: anyone picking this up later should be able to rebuild the query, understand why the threshold sits where it does, and follow the same triage path.

Focus
Authentication anomalies and brute-force behaviour
Telemetry
Windows Security Event Logs in Splunk Enterprise
Signal
Event ID 4625, grouped by source and account
Result
80+ failed logons isolated in a defined window
Workflow

Four steps, in order.

Ingestion

Windows Security Event Logs — specifically Event ID 4625 — ingested into Splunk Enterprise and normalised so source host, account and timestamp can be queried consistently.

Detection

SPL queries correlating failed logon volume across source IP, user account and time window — the combination that separates one frustrated user from a host hammering many accounts.

Triage

Correlated events reviewed, thresholds adjusted to cut false positives without losing signal, and the decision points written down including what was ruled out.

Response

Analyst actions, escalation criteria and reusable case notes defined so the next occurrence follows a known path.

Outcome

A lab that behaves like real work.

A self-contained use case demonstrating credential-attack detection, a structured triage method, and a documented analyst workflow that would transfer to a real operations environment without rewriting.
